EVE Online announced the start of its migration from Stackless Python 2.7 to Python 3, using the futurize script on 2.4 million lines of code and manual review of approximately 20,000 behavioral differences. The announcement was made on August 25, 2026, and marks the first major Python upgrade in 16 years. This migration is significant because EVE Online is one of the largest and longest-running Python codebases in production, and its success will provide a valuable case study for other organizations facing similar legacy Python 2 migrations. It also highlights the challenges of upgrading a massive codebase while maintaining performance and stability, which is relevant to the broader Python community and software engineering at scale. The migration will use the futurize script to automatically convert Python 2 code to Python 3, followed by manual review of the ~20,000 places where Python 2 and 3 behavior differ, such as integer division (1/2 is 0 in Python 2 but 0.5 in Python 3). The announcement does not specify how they will replace Stackless, but at their conference last year they presented a solution using the carbonengine/scheduler library for their newer game EVE Frontier.

The migration to Python 3 is necessary because Python 2 reached end-of-life in 2020, and Stackless Python is no longer maintained, forcing EVE Online to find a new approach for their concurrency needs.

## [Your Executable is a SQLite Database](https://simonwillison.net/2026/Aug/24/your-executable-is-a-sqlite-database/) ⭐️ 8.0/10

Farid Zakaria has demonstrated a technique to create a SQLite database file that is also a valid Linux executable by setting the SQLite application ID to 'SELF' and arranging ELF components into SQLite tables. The accompanying 'self-exec' interpreter can extract and execute the embedded ELF code. This hack showcases a novel way to combine two common file formats, potentially enabling self-contained executables that can also be queried as databases. It could inspire new packaging and distribution methods, and highlights the flexibility of SQLite as an application file format. The technique uses the SQLite application ID field (at offset 68) set to 'SELF' to mark the file, and the ELF components are stored across multiple SQLite tables according to a specific schema. Additionally, the Linux kernel's binfmt_misc mechanism can be configured to automatically invoke the 'self-exec' interpreter for such files, with a registration command provided.

rss · Simon Willison · Aug 24, 11:38

**Background**: SQLite databases have a 4-byte application ID field that can be used to identify the application that created the file, which is often used by tools like 'file' to determine file type. The ELF format is the standard executable format on Linux, containing headers, sections, and segments that define how the program should be loaded and run. binfmt_misc is a Linux kernel feature that allows arbitrary binary formats to be executed by associating them with an interpreter.
